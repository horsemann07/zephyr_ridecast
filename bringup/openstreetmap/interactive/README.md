# RideCast Phase 2B — Offline Interactive Map (STM32H7B3I-DK)

This is a **separate Zephyr 4.5 + LVGL 9 bring-up application**. It reuses the Phase 2A generated map header; no CC3351, networking, NavBoxLib, GPS, map tile engine, or routing is involved. It does not change the production `app/` or the working Phase 2A source.

## Prerequisites

- Phase 2A map display and LVGL/touchscreen samples are already working.
- `bringup/openstreetmap/src/osm_map_rgb888.h` exists (generated by the existing `prepare_map.py` from your exported `map.png`).
- Windows PowerShell, West and SDK are working in `zephyr_workspace`.

## Folder structure

```text
bringup/openstreetmap/
├── map.png
```

To regenerate the Phase 2A header (only if needed), from the RideCast root:

```powershell
python .\bringup\openstreetmap\tools\prepare_map.py .\bringup\openstreetmap\map.png
```

## Touch tests

1. A 150% scaled view of the existing map should fill the 480×272 LCD.
2. Drag the road map with one finger. It moves until its edges reach the screen boundaries.
3. Tap `+` to zoom in, `-` to zoom out. The label shows 100%, 125%, 150%, 175% or 200%.
4. A red centre marker stays stationary while the map moves beneath it.
5. OSM attribution stays visible in the bottom-left corner.

**Note:** At 100% the underlying Phase 2A bitmap is 480×272—exactly the LCD size—so panning is intentionally disabled by the boundary clamp. Zooming uses pixel scaling, **not higher-resolution map tiles**. Text and roads may become blurry. This is a UI interaction test only.

## Pass criteria

- Pan responds to touch without crashes.
- Zoom buttons work and show the updated percentage.
- Image never exposes blank margins beyond its boundaries.
- Marker stays at the centre; touch coordinates match the expected movement.
- No unexpected reboots or display corruption.

## Troubleshooting

- **`osm_map_rgb888.h` not found:** run the existing Phase 2A image converter.
- **No touch:** check `CONFIG_LV_Z_POINTER_FROM_CHOSEN_TOUCH=y` and `CONFIG_LV_Z_POINTER_INPUT=y` in `build/zephyr/.config`.
- **Colors swapped:** the existing converter emits B,G,R bytes for RGB888; check the generated header and image color format.
- **Sluggish zoom:** image resampling is CPU-intensive. This test uses nearest-neighbour scaling to reduce overhead.
- **Firmware too large:** check the FLASH usage shown in the West build output; the raw bitmap consumes 391,680 bytes.

This demonstration has not been hardware-tested on the user's board by the assistant.
