# RideCast — STM32H7B3I-DK Bring-Up Guide

**Platform:** Windows PowerShell (native Windows build, **not WSL**)  
**Board:** STM32H7B3I-DK (`stm32h7b3i_dk`)  
**RTOS:** Zephyr v4.5.0  
**Purpose:** Validate the Windows/Zephyr environment, STM32, serial console, LED, LCD, LVGL, touchscreen, and an OpenStreetMap LCD preview **before** integrating CC3351. An optional Google Maps Static API PC-only check is documented in Phase 2C.

> Every terminal command below is on **one physical line**. Run commands in order. Stop at a failed check and diagnose it before moving on. All tests reuse the **same project-root `build/`** directory; the next test overwrites the previous build.

## 1. Check hardware (no code)

1. Verify the silkscreen says **STM32H7B3I-DK**, not STM32F7 or another H7 board.
2. Check that the 480×272 LCD and touch ribbon connections are seated correctly.
3. Connect the board's **ST-LINK USB** connector to the PC with a data-capable cable.
4. Check that Windows detects an ST-LINK device. In **Device Manager**, locate its virtual serial **COM port** under **Ports (COM & LPT)** (if the driver exposes one).
5. Leave **BP-CC3351 disconnected** until after display and touch are verified.

**Pass:** Correct board, good power, ST-LINK detected; record the assigned COM number.

Open **Windows PowerShell**, not WSL, and run:

cd C:\Users\ragha\workspace\navyantra\zephyr_ridecast

- STM32CubeProgrammer: https://www.st.com/en/development-tools/stm32cubeprog.html

## 3. Check the Zephyr 4.5 workspace

### 3.1 Check the Git submodule

From the project root:

```powershell
git -C zephyr_workspace\zephyr status
git -C zephyr_workspace\zephyr describe --tags --exact-match
git submodule status
```

The desired tag is `v4.5.0`. If the clone is valid but the wrong revision is checked out:

```powershell
git -C zephyr_workspace\zephyr checkout v4.5.0
```

**Important:** You previously encountered a Windows `Permission denied` error while registering the submodule. If `git -C ... status` fails, repair that Git/Windows permission problem **before** proceeding; do not blindly remove and re-download the repository. The Zephyr path should be a valid Git submodule when finished.

### 3.2 Create and activate Python environment

From the project root:

```powershell
py -3 -m venv zephyr_workspace\.venv
.\zephyr_workspace\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip west
```

If the virtual environment already exists, skip the first command. If PowerShell blocks activation, see Microsoft's execution policy documentation; don't run the entire development toolchain in WSL as a workaround.

### 3.3 Initialize West and download modules

```powershell
cd zephyr_workspace
if (-not (Test-Path .west\config)) { west init -l zephyr }
west update
python -m pip install -r zephyr\scripts\requirements.txt
west zephyr-export
```

`west init -l zephyr` uses the Zephyr **Git submodule** as the West manifest source. `west update` downloads the Zephyr-managed modules; those do not each need to be tracked in the RideCast Git repository.

### 3.4 Install/verify the ARM toolchain

```powershell
west sdk install --toolchains arm-zephyr-eabi
west topdir
west list
west boards | Select-String stm32h7b3i_dk
```

If you already installed a compatible Zephyr SDK, you can skip the installation command. Make sure the SDK is a **Windows** SDK, not a Linux/WSL SDK.

**Pass:** West reports the `zephyr_workspace` directory, lists modules and recognizes `stm32h7b3i_dk`.

## 4. First custom application — Zephyr boot + UART + LED

We will create **three small source/configuration files** in `bringup/`, **not** in `app/`.

### 4.1 Create directories/files

Return to the project root:

```powershell
cd ..
New-Item -ItemType Directory -Force bringup\src
New-Item -ItemType File -Force bringup\CMakeLists.txt
New-Item -ItemType File -Force bringup\prj.conf
New-Item -ItemType File -Force bringup\src\main.c
```

Open these files in VS Code, copy the following contents, and save them.

### File: `bringup/CMakeLists.txt`

```cmake
cmake_minimum_required(VERSION 3.20.0)

set(ZEPHYR_BASE "${CMAKE_CURRENT_LIST_DIR}/../zephyr_workspace/zephyr" CACHE PATH "Zephyr source")
find_package(Zephyr REQUIRED HINTS "${ZEPHYR_BASE}")

project(stm32_board_bringup LANGUAGES C)

target_sources(app PRIVATE src/main.c)
```

### File: `bringup/prj.conf`

```ini
CONFIG_GPIO=y
CONFIG_SERIAL=y
CONFIG_CONSOLE=y
CONFIG_UART_CONSOLE=y
CONFIG_PRINTK=y
```

### File: `bringup/src/main.c`

```c
#include <zephyr/kernel.h>
#include <zephyr/device.h>
#include <zephyr/devicetree.h>
#include <zephyr/drivers/gpio.h>
#include <zephyr/sys/printk.h>

#define LED_NODE DT_ALIAS(led0)

static const struct gpio_dt_spec led = GPIO_DT_SPEC_GET(LED_NODE, gpios);

int main(void)
{
    int ret;
    uint32_t count = 0U;

    printk("\n=== RideCast STM32H7B3 bring-up ===\n");

    if (!gpio_is_ready_dt(&led)) {
        printk("ERROR: LED GPIO not ready\n");
        return 0;
    }

    ret = gpio_pin_configure_dt(&led, GPIO_OUTPUT_INACTIVE);
    if (ret < 0) {
        printk("ERROR: LED GPIO configure failed: %d\n", ret);
        return 0;
    }

    printk("GPIO initialized. Starting heartbeat...\n");

    while (1) {
        ret = gpio_pin_toggle_dt(&led);
        if (ret < 0) {
            printk("ERROR: LED toggle failed: %d\n", ret);
        }

        printk("STM32 alive: %u\n", count++);
        k_sleep(K_SECONDS(1));
    }

    return 0;
}
```

On this board, Zephyr maps `led0` to user red LED **LD1**, and the console is on **USART1** connected to ST-LINK. The board UART defaults to **115200 baud**.

### 4.2 Build and flash

From the project root, with the Python virtual environment activated:

```powershell
cd zephyr_workspace
west build -p always -b stm32h7b3i_dk -s ..\bringup -d ..\build
west flash -d ..\build
```

Open the ST-LINK COM port in PuTTY or another terminal with **115200, 8-N-1, no hardware flow control**. If necessary, reset the board after opening the terminal to see the startup banner.

Expected example:

```text
=== RideCast STM32H7B3 bring-up ===
GPIO initialized. Starting heartbeat...
STM32 alive: 0
STM32 alive: 1
STM32 alive: 2
```

The red user LED should toggle once each second.

**Pass:** The firmware flashes, logs appear, and the LED toggles.

## 5. LCD test — without LVGL

Zephyr already includes a display sample. From **`zephyr_workspace/`**:

```powershell
west build -p always -b stm32h7b3i_dk -s .\zephyr\samples\drivers\display -d ..\build
west flash -d ..\build
```

**Expected:** Color test regions appear on the 480×272 LCD, and an area changes over time. This verifies the display driver, LTDC and framebuffer path. Exact patterns depend on the sample/pixel format.

**Pass:** You see correctly rendered colors and visible updates; no crashes or repeated resets.

## 6. LVGL test

Run Zephyr's supplied LVGL sample, still from **`zephyr_workspace/`**:

```powershell
west build -p always -b stm32h7b3i_dk -s .\zephyr\samples\subsys\display\lvgl -d ..\build
west flash -d ..\build
```

**Expected:** `Hello World` and a counter that increments once per second. If the appropriate touch/pointer input is available in the LVGL configuration, the sample may show an interactive button instead of a plain label.

**Pass:** Text appears and the counter updates steadily without display artifacts or crashes.

## 7. Touchscreen test

Zephyr 4.5 provides a more direct hardware test than relying only on the LVGL button. The board devicetree defines the FT5336 controller on I2C4 and selects it as `zephyr,touch`.

From **`zephyr_workspace/`**:

```powershell
west build -p always -b stm32h7b3i_dk -s .\zephyr\samples\subsys\input\draw_touch_events -d ..\build
west flash -d ..\build
```

**Expected:** Touching different places on the LCD draws a small marker/plus at the corresponding touch location. Check the four corners and middle; the coordinates should not appear inverted or swapped.

**Pass:** The marker follows your finger at the expected positions. If this fails, check the FT5336 configuration and I2C/touch inputs before building a custom LVGL UI.

## 8. Inspect BP-CC3351 — no connection yet

Before electrically connecting the BoosterPack to the STM32:

1. Record the BP-CC3351 PCB revision and inspect all power-supply jumpers.
2. Check host power requirements and logic voltages against the actual BoosterPack hardware guide.
3. Identify **Wi-Fi SPI**: CLK, MOSI, MISO, CS, IRQ and reset.
4. Identify **BLE UART HCI**: TX, RX, RTS, CTS and any additional enable/interrupt signals specified by TI.
5. Confirm the STM32 interface pins are free and accessible. Cross-check both board schematics before wiring.
6. Do **not** attach both boards or power the BoosterPack until those checks pass.

TI hardware guide: https://software-dl.ti.com/simplelink/esd/simplelink_wifi_sdk/10.10.01.08/exports/docs/WiFi-toolbox/html/cc33xx/BP-CC33X1_HW_UserGuide.html

**Pass:** Recorded connector mapping and safe power plan. Integration comes later.

## Common problems

| Problem | First checks |
| --- | --- |
| `zephyr_workspace/zephyr/.git Permission denied` | Fix Git/submodule permissions first; preserve the downloaded clone if recoverable. |
| `west` not found | Activate `zephyr_workspace/.venv` and install West in it. |
| `stm32h7b3i_dk` not found | Verify Zephyr revision and run `west update`. |
| CMake cannot find Zephyr | Run `west zephyr-export`, ensure the submodule and local CMake path exist. |
| Toolchain not found | Install the Windows Zephyr ARM SDK; rerun a pristine build. |
| `STM32_Programmer_CLI` missing | Install STM32CubeProgrammer and make its CLI discoverable. |
| ST-LINK device not found | Check board power, USB cable, driver, Windows Device Manager and other tools holding ST-LINK. |
| No UART output | Check correct ST-LINK COM port, 115200 8-N-1, reset after opening terminal, verify device is flashed. |
| LED not blinking | Check debug logs, board model, `led0` mapping and runtime boot. |
| LCD black | Verify display sample built for correct board, LCD power/backlight, LTDC and external SDRAM initialization. |
| Touch doesn't respond | Run the touch-specific sample; check FT5336/I2C/interrupt and chosen touch node. |

# Phase 2 — OpenStreetMap LCD Preview (after Checks 1–8)

**Objective:** Confirm that a **real OpenStreetMap view** is readable on the STM32H7B3I-DK **480 × 272 LCD**. This is a separate **offline, static-image display test**, not a live mapping/navigation implementation. **No CC3351, Wi-Fi or Internet connection is required on the STM32.** Do not confuse a successful preview with proof that online tiles, GPS, routing, zoom or panning work.

The test uses Zephyr's native `display_write()` API (not LVGL) so it isolates the LCD and image rendering. Later we can build a touch-enabled LVGL map UI after this simple test passes.

## Phase 2 folder layout

```text
zephyr_ridecast/
├── bringup/
│   ├── README.md                 # Phase 1 + Phase 2 instructions
│   └── openstreetmap/
│       ├── CMakeLists.txt
│       ├── prj.conf
│       ├── map.png               # You manually export this; do not commit it blindly
│       ├── osm_map_preview.png   # Generated PC preview
│       ├── tools/
│       │   └── prepare_map.py    # Converts PNG to C array; does NOT fetch tiles
│       └── src/
│           ├── main.c
│           └── osm_map_rgb888.h  # Generated image data; ~392 KB binary payload
├── app/                          # Remains untouched
├── cc335x_port/                  # Remains untouched
├── zephyr_workspace/
└── build/                        # Same shared directory as Phase 1
```

Obtain the four *source* files (`CMakeLists.txt`, `prj.conf`, `src/main.c`, `tools/prepare_map.py`) from the accompanying Phase 2 files. `osm_map_rgb888.h` is generated after you export your map; do not create it manually.

## Phase 2A.1 — Export a real OSM map (on your Windows PC)

1. Open **https://www.openstreetmap.org/** in a browser.
2. Navigate to the city/road area you want to preview and select a suitable zoom level. At 480 × 272 pixels, choose a view with fewer road labels so they remain readable.
3. Choose **Share → Image**, choose **PNG**, and export/download *one selected view*. This is a manual one-image export, not bulk tile downloading.
4. Save the exported PNG as `bringup/openstreetmap/map.png`. The converter adds visible `(c) OpenStreetMap contributors` attribution to the LCD image.

The OpenStreetMap website supports exporting a rendered map image through its **Share** tool. Keep contributor attribution visible. The public tile service does not allow bulk/offline tile prefetching; use a suitable tile/data provider for any future full offline product. See https://wiki.openstreetmap.org/wiki/Export and https://operations.osmfoundation.org/policies/tiles/.

## Phase 2A.2 — Convert the PNG to firmware image data

From the **RideCast project root**, with your Windows Python environment active:

```powershell
python -m pip install pillow
python bringup\openstreetmap\tools\prepare_map.py bringup\openstreetmap\map.png
```

Expected files:

```text
bringup/openstreetmap/osm_map_preview.png
bringup/openstreetmap/src/osm_map_rgb888.h
```

Open `osm_map_preview.png` **on the PC** first. It shows exactly the 480 × 272 composition we intend to display (a small top-left status label and bottom attribution). The image is embedded as **RGB888** byte data in the firmware; it does not require a filesystem or runtime PNG decoder on STM32.

**Memory note:** The raw pixels require **480 × 272 × 3 = 391,680 bytes** of nonvolatile image storage, plus the LTDC framebuffer in SDRAM. The generated C header can be much larger as text. This is acceptable for a one-image proof of concept, but not the approach for full online maps.

## Phase 2A.3 — Build and flash the static map test

From the **RideCast project root**, with Zephyr's Windows virtual environment activated:

```powershell
cd zephyr_workspace
west build -p always -b stm32h7b3i_dk -s ..\bringup\openstreetmap -d ..\build
west flash -d ..\build
```

**Important:** The pristine `-p always` replaces the previous Hello World, LCD, LVGL or touch test firmware in the shared `build/` directory.

**Expected on LCD:** An actual OpenStreetMap road view matching `osm_map_preview.png`, a small **OSM: OFFLINE DISPLAY TEST** label, and **OpenStreetMap contributors** attribution along the bottom. No animation or touch movement is expected in this stage.

**Expected serial log (115200 baud):**

```text
RideCast Phase 2 - OpenStreetMap static preview
LCD: 480 x 272, pixel format 0x...
Map displayed. This is OFFLINE ONLY; no Wi-Fi/network tested.
```

**Pass:** The LCD image is sharp enough to identify roads and labels, colors are correct, and the map remains stable without crashes. Note the closest readable road labels and any distortion, tearing or unwanted cropping. If red and blue appear reversed, confirm the Zephyr 4.5 RGB888 framebuffer byte order and generated header before changing the driver.

**Fail and stop:** A black display, incorrect colors, CMake errors, or firmware size errors. Verify Check 5 (LCD) and Check 6 (LVGL) passed first. If the compiler reports `osm_map_rgb888.h` missing, run the converter in Phase 2A.2. If the board reports a pixel format other than RGB888, check `CONFIG_STM32_LTDC_RGB888=y` in this test's `prj.conf` and rebuild pristinely.

## Phase 2B — Later, after CC3351/network bring-up (not part of this test)

- Use Zephyr + LVGL for a visible map viewport and buttons.
- Handle FT5336 touch events for pan/zoom controls.
- Fetch **only required, visible** map tiles over Wi-Fi using a provider that permits the planned usage, with proper attribution, identification and caching. Do not implement bulk tile prefetch against `tile.openstreetmap.org`.
- Add tile caching, image decoding, pan/zoom, failure behavior and optional GPS/navigation payloads.
- Measure RAM, flash, CPU and frame rate on the STM32 before deciding whether a live map UI is practical for RideCast.

**Reminder:** The intended RideCast product remains a lightweight wireless-to-UART adapter; the embedded map UI here is a **development/board-capability test**, not a decision to move navigation application logic into the adapter.

# Phase 2C — Optional Google Maps Static API Check (Windows PC only)

**Purpose:** Check what an official **Google Maps Static API** road map looks like at **480 × 272**, matching the STM32H7B3I-DK LCD resolution. **This step runs in a Windows browser only**: it does *not* flash Google Maps data to the STM32, prove the CC3351 network path, or implement navigation on the board. It is **not required** to pass the OpenStreetMap bring-up.

> **Vehicle-product restriction — read before implementation:** Google Maps Platform Terms of Service, section **3.2.3(f), No Use in Embedded Vehicle Systems**, prohibits use of Google Maps Core Services in connection with a customer application or device embedded in a vehicle, subject to expressly stated exceptions. **Do not adopt the Maps Static API as RideCast's in-vehicle map solution without obtaining appropriate contractual permission/confirmation from Google.** This optional PC-only API check is for evaluating an image in a non-vehicle development environment. The OpenStreetMap preview remains our default LCD hardware test. See: https://cloud.google.com/maps-platform/terms

## Phase 2C.1 — Set up the Google API project

1. Open **https://console.cloud.google.com/** on the Windows PC.
2. Create/select a Google Cloud project and **enable billing**. Billing is required even for calls that fall within the free monthly usage cap.
3. Enable **Maps Static API** (not the Maps JavaScript API).
4. Create an API key; restrict it to **Maps Static API** and apply appropriate application restrictions for the actual request method. Directly testing a URL in a browser may not provide a referrer suitable for website-referrer restrictions; use a compatible restriction for the test and never leave the key unrestricted permanently.
5. Set a low **API quota** and configure billing budget alerts. Alerts are notifications, not a hard spending cap. Do not put the API key in `build.py`, firmware, source files, commits or this README.

Official setup: https://developers.google.com/maps/documentation/maps-static/get-api-key

## Phase 2C.2 — Display a 480 × 272 Google map on the PC

From **Windows PowerShell**, enter your key into a local variable (this prompts without showing the key as you type):

```powershell
$env:GOOGLE_MAPS_API_KEY = Read-Host "Maps Static API key"
```

Then open a 480 × 272 road map of Hyderabad in your default browser:

```powershell
Start-Process "https://maps.googleapis.com/maps/api/staticmap?center=17.3850,78.4867&zoom=14&size=480x272&maptype=roadmap&format=jpg-baseline&key=$env:GOOGLE_MAPS_API_KEY"
```

**Note:** Opening the URL in a browser can put the API key in browser history, browser tooling, and request logs. Use a restricted throwaway development key for this short PC-only test, revoke it when finished, and do not share the URL or screenshots that expose the key. Delete the variable after the test:

```powershell
Remove-Item Env:\GOOGLE_MAPS_API_KEY
```

**Expected:** One 480 × 272 Google road-map image (not an interactive map), with Google's supplied branding/attribution left intact. If Google returns an error image or text, check that the Maps Static API is enabled, billing is active, and your key restrictions permit the request. Do not crop, hide or overwrite the branding/attribution.

**Pass for PC-only check:** Google returns the correct 480 × 272 image and the roads/labels appear readable at that size. **This does not count as an STM32 LCD pass.**

Google's image parameters are documented at: https://developers.google.com/maps/documentation/maps-static/start

## Phase 2C.4 — What would be required to show a *live* Google map on the STM32?

**Not included in the current bring-up and not approved for a vehicle product.** After checking the platform licensing and getting suitable authorization if needed, a *separate* lab implementation would need a network connection (via CC3351 or a PC bridge), HTTPS fetching, image decoding (for example baseline JPEG), and an LVGL/display image path that renders the freshly requested map in RAM. A direct Maps Static API call returns **one image per request**; pan/zoom would require new requests and application logic. It does not include live routing, GPS or turn-by-turn navigation.

**Do not download a Google Maps image and permanently embed it as `map.h`, `map.png`, an external-flash asset or firmware data.** Google Maps Platform restricts caching, redistribution and other uses of Maps content, and requires visible attribution. Unlike Phase 2A's appropriately attributed OpenStreetMap export, this is **not an offline image embedding workflow**.

Relevant terms: https://cloud.google.com/maps-platform/terms
